What memory is, and why a stateless model needs one

An LLM call is fundamentally stateless: the model knows nothing beyond the tokens sent to it in that one request. Everything that looks like "remembering" in a chat product is an engineering layer built around the model, deciding what from the past to re-inject into the next prompt. Three things get conflated and are worth separating:

Context window

Raw text capacity for one call. Not persistence — close the session and it's gone, and everything in it costs latency/money whether relevant or not.

RAG

Retrieval over a static corpus (crop advisories, price sheets). Answers "what does the corpus say" — stateless, query-matched document lookup.

Memory

A persistent, mutable, user-scoped store of what the interaction itself produced — facts stated, preferences revealed, advice given — updated as things change.

The distinction that matters

RAG is stateless document retrieval. Memory has to manage evolving, sometimes contradictory user state over time.

The standard academic framing comes from CoALA (Cognitive Architectures for Language Agents — Sumers, Yao, Narasimhan & Griffiths, Princeton/DeepMind), which borrows Endel Tulving's memory trichotomy from cognitive psychology and has since become the industry-default vocabulary — Letta, Mem0 and LangChain all build on it:

  • Working memory — the live, in-context state of the current conversation. Gone when the session ends unless something is deliberately promoted out of it.
  • Episodic memory — records of specific past events ("on 12 June the farmer asked about pest damage in cotton and was told to apply X"). Timestamped, instance-specific.
  • Semantic memory — generalized facts abstracted from any one conversation ("this farmer grows cotton and wheat on 2 acres in Yavatmal"). Closer to a profile than a transcript.
  • Procedural memory — how to do things: learned rules, standing preferences, the agent's own operating conventions.

Without an explicit memory layer, a chat system degrades in specific, observable ways: the same identifying questions get re-asked every session; nothing about the service compounds or personalizes over time; a farmer who messages on WhatsApp Monday and calls the voice line Thursday is treated as two strangers; and the agent has no way to reference, quote, or build on its own prior advice — "the fertilizer plan you gave me last month" is simply unanswerable.

Put plainly: memory is what you persist — and whatever a system chooses not to persist becomes a cost the human pays instead, re-explaining the same land, crop, and circumstances every time they need something. The clearest way to think about a farmer's core profile is as a ledger of what they depend on to get a useful answer — kept once, so it's never asked for twice.

The design tradeoffs that actually matter

What to store. A raw transcript is lossless and cheap to write but noisy and expensive to retrieve from, and it re-exposes every raw utterance on every future pull. Extracted facts or periodic summaries are cheaper to retrieve and can be structured — at the cost of fidelity: a bad fact that enters a summary can poison every future turn that relies on it. Most production systems land on a middle position worth naming directly — call it intentional memory: deliberately decide what's worth keeping out of everything logged, rather than defaulting to keep-everything or leaving it entirely to whatever the model happens to notice in a given turn.

When to write. Writing after every turn maximizes fidelity but adds an extraction call — and a latency/cost tax — to every single message. End-of-session or batched consolidation is cheaper and lets a system reflect over a whole conversation before deciding what's durable. Writing only on an explicit signal ("remember this") is cheapest and most auditable, but misses facts the user never thought to flag.

How to retrieve. Pure recency is simple but blind to relevance. Semantic similarity surfaces old-but-relevant facts, at the cost of retrieval latency and occasional confident wrongness. Structured profile fields (crop, district, land size) are cheapest and most reliable — no search needed — but only cover what was modeled in advance. Production systems increasingly don't pick one: Zep merges semantic, keyword, and graph-traversal retrieval via reciprocal rank fusion because no single method is sufficient alone.

The real risks

Staleness — a fact recorded once ("grows cotton") silently outliving its truth. Privacy/consent — anything stored is personal data needing disclosure and a way to view, correct, or delete it; extraction attacks against agent memory are now an active research area. Retrieval cost — every vector search or structured fetch adds latency to every turn, which matters acutely on WhatsApp or a voice call. Cross-contamination — one study of shared-state agents found that with no attacker involved at all, careless scoping produced contamination rates of 57–71% between unrelated users' sessions. For a multi-farmer system, strict per-user namespacing isn't optional.

02

How the best systems elsewhere do it

Concrete, currently-documented examples — what each actually stores and retrieves, not a generic description — with the one lesson most transferable to a farmer-advisory bot.

ChatGPT — Saved Memories + Reference Chat History

Explicit facts, plus a separately-maintained inferred profile

Two distinct mechanisms run side by side. Saved memories are discrete, user-visible, timestamped entries — added on request or saved proactively when the model judges something durable was said — injected into the system prompt and fully viewable, editable and deletable by the user. Reference chat history is a separate, opaque profiling pass: it periodically compiles "Assistant Response Preferences," "Notable Past Conversation Topics," and confidence-scored "Helpful User Insights" (name, profession, location) plus a rolling window of recent conversation summaries — with no interface to inspect or edit individual inferred entries, only an on/off toggle. In 2026 OpenAI added "Dreaming": a background job, run during account idle time, that reconciles and rewrites memory entries rather than only capturing what was explicitly said (a stored "going to Singapore in July" auto-updates to "went to Singapore" once the trip has passed) — OpenAI reported an internal factual-recall eval jumping from 41.5% to 82.8% after shipping it.

Lesson for mahaVistaar Split explicit, user-controllable facts (crop, land size, district) from softer inferred signals, and give them different consent/visibility treatment. The "Dreaming" idea — periodically reconciling facts against the calendar rather than writing once and trusting it forever — is exactly what a seasonal advisory bot needs.
OpenAI Help Center · Embrace The Red technical teardown · Dreaming V3 coverage

Mem0 — open-source memory layer

Extract → consolidate → retrieve, Qdrant + Postgres underneath

After each interaction, Mem0 extracts durable facts, reconciles them against what's already stored (updating or superseding contradictions rather than appending blindly), and on the next call retrieves only the relevant subset — never the whole transcript. It orchestrates a vector store (Qdrant by default) for semantic recall plus Postgres for structured history behind a simple add/search API. On the LOCOMO long-conversation benchmark, Mem0's own paper reports a 26% relative accuracy improvement over OpenAI's memory baseline, a 91% reduction in p95 latency, and over 90% token-cost savings versus stuffing full history into context.

Lesson for mahaVistaar Extracting crop = cotton, district = Yavatmal, land_size = 2 acres as structured, updatable facts — with real contradiction handling when a farmer switches crops — is far cheaper at inference time than re-searching a raw transcript on every WhatsApp message.
mem0.ai · Mem0 paper (arXiv:2504.19413)

Letta / MemGPT — memory as an operating system

Core / recall / archival tiers, paged like RAM, disk, and cold storage

MemGPT's founding idea, now the production framework Letta: treat the model's context window as scarce RAM and give the system "virtual context management" — paging information in and out the way an OS pages between memory and disk. Three tiers: core memory, small and always in-context, editable by the agent's own tool calls; recall memory, the full searchable history outside the active context; archival memory, long-term storage (Postgres + pgvector) queried by similarity via explicit tool calls. The distinguishing choice is that the agent itself decides when to page memory in and out, rather than a fixed pipeline deciding for it.

Lesson for mahaVistaar A small, always-injected "core memory" block per farmer (crop, land, location, language) costs almost nothing and guarantees the agent never re-asks the basics mid-conversation, while full advisory history stays in cheaper storage and is pulled in only when a query actually references the past.
MemGPT paper (arXiv:2310.08560) · Letta docs

Zep / Graphiti — temporal knowledge-graph memory

Bi-temporal facts, hybrid retrieval, no LLM call in the retrieval path

Zep's memory engine, Graphiti, represents facts as nodes and edges in a graph rather than flat text chunks, and is explicitly bi-temporal: every fact tracks both when it was true in the real world and when the system learned it. A contradicting new fact invalidates the old one rather than deleting it — the system keeps a full, queryable history of what was true when. Retrieval fuses semantic embedding search, BM25 keyword search, and graph traversal via reciprocal rank fusion, deliberately without an LLM call in the loop, for roughly 300ms p95 latency. On LongMemEval, Zep reports aggregate accuracy improvements up to 18.5% over a full-context baseline (individual tasks over 100% higher), a 90% latency reduction, and context-token usage under 2% of the full-transcript baseline (1.6k vs 115k tokens) — with Zep+GPT-4o at 2.58s median latency against 28.9s for full-context+GPT-4o.

Lesson for mahaVistaar This is the single most relevant idea in this whole review for agriculture. Truth here is inherently seasonal: "farmer grows cotton" is true for one season and false the next; "farmer applied urea on 14 June" stays permanently true even after harvest. A flat profile store can't represent this and will eventually advise against an outdated crop assumption. Facts need a valid-from/valid-to, not a silent overwrite.
Zep/Graphiti paper (arXiv:2501.13956) · Zep engineering blog

Amazon Alexa+ — household-scoped personalization

Bootstrapped from account data, explicit teaching, multi-person constraints

Alexa+ combines account-derived context (purchase history, saved addresses, watch/listen history) with explicitly taught durable facts and connected personal data. Amazon's own illustrative example is deliberately multi-person: "if you are planning a dinner for the family, Alexa+ can remember that you love pizza, your daughter is vegetarian, and your partner is gluten-free." Amazon reported roughly double the conversation engagement versus the prior Alexa.

Lesson for mahaVistaar A single WhatsApp number often serves a whole farm household — a son checking mandi prices, the farmer handling crop advisory. Memory needs to resolve "whose fact is this" under one shared identity the same way Alexa+ resolves competing dietary constraints, and bootstrapping from existing registration/enrollment data (Agristack, scheme enrollment) rather than only learning turn-by-turn is directly available here.
aboutamazon.com — Introducing Alexa+

LangGraph — the checkpointer / store split

Short-term thread state vs. a namespaced long-term document store

LangGraph formalizes the split at the infrastructure level: a checkpointer persists a single conversation thread's state so it can pause and resume, while a separate store holds long-term memories as JSON documents organized by namespace — explicitly recommended to be the user's identity, not the conversation thread, so every store operation for a given farmer hits the same namespace no matter how many separate sessions they've had.

Lesson for mahaVistaar Namespace by farmer identity, never by session or thread id — this is precisely the discipline that section 3 shows is currently at risk.
LangChain — Launching Long-Term Memory Support in LangGraph

An identity paradox

Langfuse's own userId field is "anonymous" or null on every trace sampled — but the actual text sent to the model tells a different story. Every vistaar-agent prompt embeds a line pulled from the auth token itself:

**Logged-in farmer ID (from token):** 65844210062
**Logged-in farmer (Agristack-linked):** ✅

A stable, government-registry-linked identity is already flowing through every authenticated request — it just isn't the identity Langfuse is keyed on, and, per Section 5, isn't fully what the app's own session/memory keying uses either.

Finding — new sessions are the norm, which raises the stakes on user-level memory

One farmer asked six obviously sequential questions about the same groundnut crop — land preparation → pod filling → pest/disease control → pod borer control → fertilizer at pod-filling → fertilizer after planting — across six different sessionIds in 19 minutes (16:34:41 through 16:53:36). Each one's moderation-observation input showed zero prior turns: every one of the six was logged as a brand-new, historyless conversation.

This is by design, not a bug — session ids are deliberately not mapped to user ids, and a farmer is free to start a new conversation as a new session at any time. That's precisely why continuity can't be the session layer's job at all: it has to live entirely at the farmer-identity level, in the profile/episodic memory described in Section 5. The backend already accounts for this in principle — preload_farmer_profile() is designed to fire on the first turn of every new session, whenever a resolvable farmer identity exists, precisely so a fresh session id doesn't mean a fresh farmer. What's notable in this sample is that none of the six fresh-session first turns showed any injected profile content — worth confirming directly whether that's simply because this farmer had no saved profile facts yet, or whether preload isn't reliably firing/rendering into the prompt. Either way, the finding reframes the priority: not "stop sessions from resetting," but "prove user-level memory is actually doing the job it's designed to do across every reset."

04

Use cases worth adding

Several of these independently match priorities the team had already voted on in its own planning session — noted inline where that overlap is direct.

  1. Prove user-level memory is actually bridging every session reset.Sessions are deliberately not mapped to users, so a farmer starting fresh is normal, not a bug — which means profile preload and episodic recall are the only thing that can carry continuity across visits. Confirm that's firing and populating reliably, not just present in code.
  2. Make "tell us once" the actual design target.The team's own framing: memory should read like a ledger of what a farmer depends on, so the technology's purpose is served with minimal incremental input from them — every repeated question is a design failure, not a neutral cost. One of the most highly prioritized outcomes in the team's own planning session.
  3. An always-on "core memory" block per farmer.Crop, land size, district, irrigation, language — auto-populated at first contact and injected on every turn (Letta's core-memory pattern), so a returning farmer never repeats identifying context.
  4. Make past advice genuinely referenceable.Write an explicit episodic record ("advice given: X, on date Y, for topic Z") at the moment the agent gives a recommendation, rather than leaving all capture to the model's own discretion.
  5. Seasonal/temporal fact versioning.Give crop and land-use facts a valid-from/valid-to instead of a flat overwrite, so "switched to soybean this kharif" doesn't erase last season's cotton data — Zep's bi-temporal lesson, directly applicable.
  6. Household-aware memory.Resolve "whose fact is this" when one phone number serves a farming family with different roles, rather than assuming one identity per number.
  7. Extend identity + memory to the voice channel.No equivalent "logged-in farmer" marker was found on voice traces — a farmer who called in gets none of what the text channel already learned about them.
  8. Forced periodic consolidation, not purely tool-call-gated capture.Mirrors ChatGPT's "Dreaming" pattern — a background pass that writes and reconciles memory, instead of relying entirely on the model choosing to call a save tool that turn.
  9. A farmer-facing "what mahaVistaar knows about me" view.View, correct, and delete stored facts — matches the ChatGPT precedent, and matters more here given this is government-linked, Agristack-tied personal data.
  10. Let the suggestions agent see more than the last exchange.It's currently deliberately blind to anything before the current turn, so it can't propose "want to check pest control for the groundnut you asked about earlier?" even when that's the obviously better suggestion.
  11. Feed aggregated community memory back into regional decisions, not just individual advice.Also from the team's own planning session, and distinct from personal memory entirely: patterns across many farmers in a region — recurring problems, unmet needs — aggregated and anonymized, informing actual notifications or policy attention for that area, not just one farmer's answer.
  12. Decide a real policy for guest/unauthenticated users."Logged-in" is already a stated boundary condition for memory, not an oversight — so this isn't about whether to gate it, but what happens instead for the roughly half of sampled traffic with no resolvable identity today. Even ephemeral, session-scoped-only memory would beat the current silent no-op.
05

The current mh-oan-api implementation, and what to build

mh-oan-api turns out to already have a genuinely more advanced memory system than its sibling repo bharat-oan-api — this is worth stating plainly before the gap list below, since it's easy to undersell what's already built.

Short-term (session) memory

Redis-backed, keyed by {session_id}_SVA, 2-hour TTL, deserialized via pydantic-ai's ModelMessagesTypeAdapter (app/utils.py). Truncation is trim_history() — turns are batched and greedily kept under an 80,000-token budget (64,000 in bharat-oan-api's equivalent); once the budget is exceeded, the oldest turns are dropped wholesale, with no summarization fallback. A client disconnect mid-stream drops that turn's write entirely. session_id defaults to a fresh UUID whenever the caller doesn't supply one (app/routers/chat.py) — expected, since session ids are intentionally not mapped to user ids (see Section 3).

Long-term memory — two parallel stores, both real and wired in

  • Episodic (app/services/memory.py) — wraps mem0.Memory over a Qdrant collection, with add_fact()/search()/update_memory()/delete_memory(), all scoped by a resolved user_id. This one does real semantic search — mem0 is configured with a genuine embedder (text-embedding-3-small, 1536-dim), and search() runs an embedded-query vector similarity lookup against Qdrant, threshold-gated at 0.3.
  • Structured profile (app/services/profile.py) — a FarmerProfile model (village, district, crops, land area, irrigation, soil type, language, open advisory threads, notes), one Qdrant point per farmer. This one does not do semantic search — its own docstring says so directly: "one point per hashed user_id; 1-d placeholder vector." Qdrant here is a plain keyed document store, looked up by exact farmer id only.
  • Both are exposed as pydantic-ai tools the model calls at its own discretion — the module's own docstring notes there is no post-session consolidation job.
  • Identity (app/services/identity.py) resolves a stable memory key from the JWT phone claim (SHA-256 hashed) with a fallback chain; explicit guest detection returns None and disables memory entirely for unauthenticated users.
  • Preload happens only on a session's first turn when no history exists yet, and only pulls the structured profile — episodic memories are recall-tool-only, never preloaded.
  • If Qdrant or mem0 is unreachable, both services fail silently with a retry backoff — memory degrades to nothing with no visible error to the user or caller.

Recommended build order

  • Fix first
    Instrument and verify profile preload actually fires and populates on every new sessionSince sessions are meant to reset freely, this is the single mechanism carrying continuity across visits — confirm it's working, not just present in code (none of six sampled fresh-session first turns for one repeat farmer showed injected profile content).
  • Fix first
    Add forced end-of-session consolidation, and make it curatorialDon't leave memory-writing entirely to whether the model happened to call a tool that turn — and per the team's own "intentional memory" principle, this should decide what's worth keeping, not just capture more often. mem0's current infer=True extraction is additive-only, which is a different thing from curation.
  • Build next
    Replace the profile store's placeholder-vector Qdrant collectionIt isn't using Qdrant's actual capability — a plain document store (Postgres/Redis JSON) removes a dependency for no loss of function.
  • Build next
    Add valid-from/valid-to to seasonal profile fieldsCrop and land-use facts need versioning so a season change doesn't silently overwrite last season's data.
  • Build next
    Define an explicit retention policy — what's kept, what ages outThe team's own proposed model, borrowed from recommendation-system design: MFU/MRU-style signals (frequently- or recently-referenced facts stay prominent) paired with LRU-style decay for what quietly fades. Keep this distinct from three separate operations: no longer surfacing a fact, actively deleting it, and a farmer explicitly invalidating/correcting one — right now the system only really has "delete."
  • Build next
    Extend identity resolution to the voice channelSame phone-hash approach, wired into the RAYA/voice path.
  • Decide
    Guest-user memory policyLogged-in is already a stated boundary condition, not an open question — what's undecided is whether unauthenticated traffic gets nothing at all, or at least ephemeral, session-scoped-only memory instead of the current full opt-out.
  • Decide
    Farmer-facing memory visibilityA view/edit/delete surface for stored facts, given the Agristack-linked personal data involved.
  • Decide
    Feed profile/episodic context into the suggestions agentCurrently limited to the immediately preceding turn by design.
  • Decide
    Backport (or explicitly decide not to) to bharat-oan-apiThe two repos currently diverge significantly on this entire axis.
06 — speculative

What becomes possible, once memory actually works

None of this exists today. It's what mahaVistaar could become if every piece in Sections 1–5 — identity-keyed memory, temporal versioning, proactive reach-out, cross-channel continuity — actually worked together. The scenarios below are built from the real crops, questions, and schemes seen in mahaVistaar's own logs.

The season remembers you

Episodic recallTemporal reasoningProactive push

A farmer asks how to prepare land for groundnut in mid-August. mahaVistaar doesn't just answer and forget — it quietly notes the crop and an implied sowing window. Six weeks later, without being asked, a message arrives: "Your groundnut should be entering the pod-filling stage now. Here's the fertilizer schedule for this stage — and a reminder about pod borer, since it's common at this point." The advisory follows the crop's actual biological clock, not the farmer's memory of when to ask again.

Not possible today: mahaVistaar only ever answers a question already asked — there's no crop-stage calendar tied to a stored sowing date, and no channel for the system to speak first.

Did it work?

Outcome trackingClosed-loop advice

A farmer is told to apply a specific pest-control measure for pod borer in groundnut. Two weeks later mahaVistaar checks back: "Last time you asked about pod borer — did the treatment help?" A one-line reply ("yes" / "no, still bad" / "couldn't get the spray") closes the loop that's currently just an open, forgotten question. The profile schema already has a field built for exactly this — open_threads — sitting unused for this purpose today.

Not possible today: advice is given once and never revisited; nothing writes a follow-up, and nothing reads the outcome back into the farmer's record even if they volunteered it unprompted.

Planning the season together

Goal-based coachingCrop-calendar planning

At the start of kharif, mahaVistaar and a farmer set an explicit goal together — not just "grow groundnut" but a target, like a yield per acre — and build a calendar of milestones from it: land prep by a date, the sowing window, the expected pod-filling stage, an eventual harvest window. Every question that season gets read against this shared plan instead of standing alone, and mahaVistaar checks in at each milestone rather than only when asked — less a Q&A tool, more a season-long planning partner holding the same plan the farmer is.

Not possible today: nothing in the current schema represents a stated goal or a calendar of milestones tied to it — open_threads tracks individual advisory topics, not a standing season plan.

One farm, one long conversation

Multi-year memorySeasonal versioning

Three years in: mahaVistaar holds a running record of what was grown each season on this specific plot, what advice was given, what the farmer reported back. A new question — "should I switch this field to soybean?" — gets answered with the field's own history in view: cotton the last two kharifs, a pest problem last year, tur before that. For a smallholder without formal land records, this becomes the closest thing to an agronomic diary of their own farm.

Not possible today: mem0's fact extraction is additive with exact-hash dedup only — it has no concept of a season boundary, so there's no structured "this was true last kharif, this is true now" to look back through.

Whoever picks up the phone

Household modelingIdentity resolution

The same phone number serves a whole household — a son checking mandi prices for tur, his father asking about fertilizer for the same tur-Godavari plot. mahaVistaar resolves this as one shared farm context with two people drawing on it: the son's price query and the father's fertilizer question both reference the same two-acre plot without either of them having to re-explain it, while personal asides (whose question it was) stay separate.

Not possible today: memory is keyed on one phone-hashed identity with no concept of multiple people sharing it, and no mechanism to tell whose statement is whose.

The rains are still three days out

External data fusionProactive push

mahaVistaar already answers "what's the forecast for Nagpur" on request. With memory, it flips the direction: it knows this farmer's cotton is at flowering stage from an earlier conversation, sees heavy rain forecast for the district three days out, and reaches out first — "Rain expected Thursday–Friday. If you were planning a pesticide spray on the cotton, consider moving it earlier." The advisory arrives while it can still change a decision, not only when asked.

Not possible today: weather lookups and crop-stage memory exist as separate, request-only tools — nothing joins them, and nothing initiates contact.

The scheme window is closing

Episodic recallProactive push

A farmer asked about the Bhausaheb Fundkar orchard-planting subsidy back in June and seemed eligible but never followed up. In early July, five days before the application window closes, mahaVistaar sends a reminder: "The orchard subsidy you asked about closes on the 12th — want help applying before it shuts?" And since it already knows the farmer's land size, district, and crop from the stored profile, it doesn't stop at reminding — it prepares a pre-filled application for them to check and submit, turning a form many smallholders abandon halfway through into a two-tap confirmation. Missing a scheme deadline because no one reminded you, or giving up partway through a form, are two of the most common, most preventable ways smallholders lose out on real money.

Not possible today: scheme conversations aren't tracked as open items with real dates attached, there's no scheduled job watching for approaching deadlines, and nothing turns stored profile facts into a pre-filled form.

Called Monday, texted Thursday, still the same conversation

Cross-channel identity

A farmer calls the voice line about a cabbage pest problem on Monday. On Thursday, the same farmer texts on WhatsApp asking about fertilizer timing for the same crop. mahaVistaar already knows about Monday's call — one relationship, reached two different ways, not two strangers who happen to share a phone number.

Not possible today: voice traces show no equivalent farmer-identity marker to the text channel's — the two appear to be memory-isolated from each other right now.

Something's moving through the district

Community-level memoryAnomaly detection

mahaVistaar notices an unusual spike: many farmers in the same taluka, within the same week, independently asking about a leaf-spot-like symptom on groundnut. Before most of them have even noticed a problem themselves, a district-wide advisory goes out to every groundnut farmer nearby — memory operating not just per-farmer, but as an early-warning system built from the aggregate pattern of what people are suddenly asking.

Not possible today: every query is handled in isolation; nothing aggregates across farmers to notice a pattern forming in near-real time.

What the district is telling the state

Community-level memoryPolicy feedback loop

The card above is farmer-facing — an early warning back out to the people asking. This one points the other way. Across a taluka, dozens of farmers have separately mentioned irrigation shortages over a season, never as a formal complaint, just as context inside ordinary questions. Aggregated and anonymized, that becomes a signal the state agriculture department can actually act on: not a chatbot transcript, but a concrete case for where a borewell scheme would matter most this year. Memory here isn't serving one farmer — it's feeding the same policy process that decides what schemes exist to ask about in the first place.

Not possible today: no aggregation layer exists above the per-farmer memory stores, and no path connects mahaVistaar's logs to any policy or resource-allocation process.

"What do you know about me?"

TransparencyFarmer agency

A farmer asks, in Marathi, "what do you know about my farm?" — and gets a clear, plain-language summary back: crop, land size, district, the last few things discussed, nothing hidden or opaque. They can correct it on the spot ("no, I switched to soybean") the same way they'd correct a person. Given this is Agristack-linked personal data, this isn't a nice-to-have — it's the difference between a system farmers trust and one they're right to be wary of.

Not possible today: the only existing read paths are internal admin/debug routes gated by an admin token — there's no farmer-facing view at all.

Worth naming honestly

Several of these — especially anything touching financial stress, debt, or risk tolerance — cross from "helpful memory" into sensitive personal data territory fast. A system that remembers enough to give genuinely personalized advice is also a system that could quietly profile vulnerability. The community→policy card carries its own version of the same risk one level up: an aggregate signal is only as fair as who's represented in it, and a policy decision built on mahaVistaar's user base could just as easily entrench whoever already has access to a smartphone as serve whoever needs the scheme most. Every one of these should ship with the same farmer-facing transparency as the "what do you know about me" card, not just the proactive-outreach features — remembering more, individually or collectively, only earns trust if what's remembered stays visible and correctable.
